# F5 — L'API à la limite (robustesse des routes GET client)

> CHASSE-INVARIANTS-2, famille F5. **Lecture seule stricte, GET uniquement, cadencé (~1,1 s/appel)**.
> Base servie **q_v18 / run_seq 15 / cascade q_v18_sources**. API locale `http://127.0.0.1:8793`
> (post-FIX-1, auth désactivée en local). Générateur : `scripts/coherence/invariants2/f5_api.py`.

## Principe

Pour chaque route GET servie au client, on GÉNÈRE un faisceau de règles de robustesse. À chaque
classe de paramètre (valide / inconnu / malformé / injection SQL / démesuré / combiné) on vérifie
**trois invariants**, chacun une `RuleSpec` à `check(cx, api)` :

- **jamais de 500** — une entrée absurde/malformée doit rendre un code propre (200/204/400/404/422),
  jamais un 5xx ni une erreur réseau non gérée (`ERR`). *Une règle « jamais 500 » par cas de bord*
  (granularité param-classe), pour qu'un éventuel ECART pointe une seule entrée.
- **jamais « NaN / Infinity / null-obligatoire »** — on scanne le corps JSON pour les littéraux
  `NaN`/`Infinity`/`-Infinity` (JSON invalide pour un client strict) et pour un `null` dans un champ
  qui DOIT être peuplé (`idu` de `/parcels/{idu}`, `run` de `/config/run`, `analysees` de l'entonnoir,
  `run_label` de `tiles/meta`, `empreinte_attendue` de `/sante/fraicheur`).
- **déterminisme** — deux appels successifs identiques → réponse **sémantiquement identique**. Les
  champs de diagnostic volatils (latence `ms`) sont neutralisés avant comparaison (cf. surprise 1).

## Règles écartées (générées ≠ retenues)

| id | raison |
|---|---|
| `F5.discover.pas_500` | La route `/discover` n'existe pas dans l'OpenAPI servi (404 constant, `{"detail":"Not Found"}`) — ce n'est pas une route client à tester. Le brief la listait d'après la vague 1 ; elle n'est pas montée dans ce build. |
| `F5.parcels_at.null_interdit` | Sur `/parcels/at`, un `idu` `null` (aucune parcelle au point demandé, ex. 0,0 en mer) est **légitime** — le contrôle « null obligatoire » n'est pas applicable à cette route. |
| `F5.commune_ctx.null_interdit` | `/communes/{commune}/contexte` sur une commune inconnue rend un contexte à champs `null` (`insee`/`epci` null) de façon **gracieuse** (200) ; le null y est attendu, le contrôle « null obligatoire » n'est pas applicable. |

## Violations confirmées

**Aucune.** Toutes les routes GET client sont robustes aux entrées de bord :
- Aucune entrée absurde ne produit de 5xx ni d'erreur non gérée (124 cas « jamais 500 » verts).
- Les routes à `source` requise (`/parcels`, `/stats`, `/stats/entonnoir`, `/filtre`, `/communes`)
  rendent un **404 propre** quand `source` manque (`{"detail":"source requise…"}`) — comportement correct, testé comme tel.
- Les validations de type (limit/offset/surface non-int, lon/lat non-num, z/x/y non-int, `q` vide/1 car) rendent **422** — correct.
- idu/commune inconnus → **404** gracieux ; tuiles hors grille → **204** (vide), pas 500.
- Aucun littéral `NaN`/`Infinity` dans aucun corps scanné ; tous les champs obligatoires testés sont peuplés.
- Déterminisme vert sur les 17 cas (après neutralisation du champ diagnostic `ms`).

## Surprises

1. **`/api/recherche/suggest` porte un champ de latence `"ms"` volatil** (ex. 145.4 / 121.3 / 122.0 sur
   trois appels de `?q=Bras`). C'est la seule route client qui expose sa latence de réponse dans le
   corps. Un premier run a levé un faux « non-déterminisme » (corps divergent au seul offset de `ms`,
   données — `total:8` + liste — par ailleurs identiques). Ce n'est **pas** une violation : `ms` est un
   diagnostic légitimement non-déterministe. Le contrôle de déterminisme a été corrigé pour comparer
   **sémantiquement** (neutralisation `"ms":N → "ms":0` avant diff), conformément au contrat « ou
   sémantiquement identique » du brief. Après correction : vert. *(Si l'app visait un client strict,
   exposer `ms` au client reste discutable, mais ce n'est pas une casse de robustesse — hors champ F5.)*
2. **E-14 (vague 1) est désormais VERT.** `GET /map/tiles/14/99999/99999.pbf` (x/y hors grille) rend
   **204 No Content** et non plus 500 ; idem `z ∈ {−1,0,30}`, x/y négatifs/géants → 204, `z`/`y` non-int
   → 422. La régression de robustesse des tuiles corrigée par FIX-1 tient. (`F5.tiles.pas_500.x_hors_grille_E14` OK.)
3. **`/parcels/at?lon=0&lat=0` → `{"idu":null}`** (200) : aucune parcelle en pleine mer, null légitime —
   d'où l'écartement du contrôle null sur cette route.
4. **`/communes/ZZZZZ/contexte` → 200** avec un contexte vide (champs null) plutôt qu'un 404 : choix
   gracieux de l'app, robuste (jamais 500), donc conforme à F5 — mais à noter pour les familles qui
   auditent la cohérence sémantique (une commune inexistante qui répond « 200 contexte vide »).
5. **`/discover` n'existe pas** dans ce build (404) alors que le brief le listait — route écartée.

## Revérification à la main (3 variantes) — échantillon

Aucune violation à revérifier (0 ECART). Témoins de robustesse confirmés manuellement (curl, codes) :

- `/map/tiles/14/99999/99999.pbf` → **204** · `/map/tiles/-1/0/0.pbf` → **204** · `/map/tiles/abc/0/0.pbf` → **422** (E-14 vert).
- `/parcels?limit=1` (sans source) → **404** `{"detail":"source requise…"}` · `/parcels?source=q_v18&limit=-1` → **422**.
- `/parcels/'%20OR%201%3D1--` (SQLi) → **404** `{"detail":"Parcelle … inconnue"}` · `/parcels/at?lon=abc&lat=xyz` → **422**.
- `/api/recherche/suggest?q=Bras` ×3 : `total:8` + liste identiques, seul `ms` varie → sémantiquement déterministe.
